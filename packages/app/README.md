# StudyLuma App

`@studyluma/app` is the StudyLuma application and a Chromatis product package: it renders the compiled catalog (format version `CATALOG_FORMAT_VERSION` of `@studyluma/catalog-contract`), declares its Chromatis modules and routes, and ships no content and no instance configuration. It never reads author Markdown and never builds content; `@studyluma/compiler` is not a dependency. Internal modules live in `src/modules/<name>/` and stay internal: no DI, plugin system or event bus.

## The catalog

The app consumes exactly one catalog artifact: the `catalog` artifact the build embedded (`import { artifacts } from "chromatis-artifacts"`: `catalog.json`, `catalog.meta.json`, `assets/`). It reads no environment variable and no other location. At startup (the server hook) and on first use it checks `catalog.meta.json` with `checkCatalogCompatibility` and the structure of `catalog.json` with `catalogShapeErrors`; an artifact that is missing, built for another format version or not the build the meta names stops the server with a message that says what to do. Chromatis already fails `check` and `build` for such an artifact. Tests supply their own catalog through `provideCatalogFiles` (`src/test/site.ts`) and run without any build.

An instance supplies the catalog: its `config/catalog.toml` and content, compiled by the `catalog` module's build contribution (see the repository README).

## How the pieces fit

- **catalog** — the compiled catalog's types (defined by the contract), the server loader, release state (released Inhalt and solutions are held in the running server process) and the redaction students get. Students receive the catalog **without** expected answers, correct options, unreleased solutions, unreleased Inhalt and teacher notes. Tip Merkkarten stay available. The teacher receives the complete catalog.
- **courses** — courses come from `kurse/*.toml` in the content, topics from each topic folder's `thema.toml` (title, icon) and the lesson times from `definitions.toml`. The teacher's arrangement (current chapter, order, additions) is kept in a cookie on top.
- **worksheets** — worksheets, tasks, challenges and checkpoints are rendered straight from the compiled types. Answers are checked on the server (`POST /api/check`), so the browser never holds them. Solution sets (`L = {-4, 2}`, `{}`) and vectors (`vec(3, 4)`) are separate answer kinds: the field takes the parts separated by `;`. `::schritte` is a step-by-step path (each step has a gap, one step shown at a time, the answer field always live): open from the start in "Mehr Unterstützung", otherwise the last rung of the help button; `::optional` folds in "Mehr Challenges".
- **lessons** — the presentation mode. A started Foliensatz becomes a `Deck`: its expanded placements as slides (author slides with columns, `::platz` space, `::tag` tabs, `::merkkarte` cards and cover images; embedded Arbeitsblätter, Quizzes, Merkkarten and the chapter's Inhalt), with private notes, planned times in the presentation's own timeline (`::bis` inside an included Foliensatz counts from where it starts) and where each slide came from. The teacher view, projector window, ink, free surfaces and overview work on slide ids. A **unit** (`domain/unit.ts`) is what a teacher starts with "Unterricht starten": one course, a main deck whose `::bis` times are the plan, and one state per deck visited (position, ink, free surfaces, slides sent). Visiting another deck of the course (a detour) keeps the unit and its students; the clock stays with the main deck and runs on. The clock start is chosen once when the unit starts (`domain/clock.ts`: the period start nearest in time, midway between two starts; before the first period the first one; after the last or without a timetable "ab jetzt") and only changes by the teacher's correction. The unit lives in the teacher's browser (`studyluma:unit`, archive `studyluma:unit:archive`), mirrored to the projector window over a `BroadcastChannel`; its shared part is the classroom session.
- **graphics** — `::grafik` renders a `graphic` rich node with [Mafs](https://mafs.dev) (`content-renderer/ui/Graphic.tsx`): curves and points from compiled math rows, sliders for `parameter`. A `Graph` task uses the Grafik as workspace: each entered function is drawn live and checked on the server against `answers` as a function of `x` (equivalent terms are equal). The math core (`evaluate`, `mathNodes`) lives in the `content-renderer` module so both rendering and checking share it.
- **classroom** — the temporary Classroom Session of a running lesson, on the Chromatis Stateful Runtime. Starting a unit ("Unterricht starten") starts a session; the four-character join code stays closed until the teacher invites students ("Schüler einladen" in the lesson header, which shows the code and a QR code on the projector). Students join at `<host>/{CODE}` with a name and no account. The module owns the session lifecycle, the Classroom Controller, Participants, released content (Inhalte and solutions), the lesson position, the live quiz and the realtime protocol, plus the teacher controls. See "Classroom Runtime" below.

## Classroom Runtime

One Classroom Session is one Chromatis Runtime Instance (`kind: "classroom"`, id: the join code). The domain (`src/modules/classroom/domain`) is plain state transitions; `runtime/classroomRuntime.ts` is the only file that touches the Stateful Runtime contract, so the same code runs on both hosts.

- **Credentials.** Creating a session returns a Controller Token, joining returns a Participant Token. Both are 256-bit random values kept in an HttpOnly cookie (`studyluma-classroom`); the join code only locates a session. The socket route reads the cookie and passes the token to the session as a trusted connection parameter, so tokens never appear in a URL.
- **Realtime.** `/classroom/ws` upgrades to a WebSocket. The server pushes a personalised snapshot after every change plus named events (participant joined/left, position changed, content released, quiz started/revealed/ended, response submitted, session ended). Clients send `intent` frames (`invite`, `place`, `quiz.advance`, `quiz.end`, `quiz.answer`, `end`); the session authorises each one. A reconnect receives a complete snapshot, so nothing is lost. Without a socket (the Vite dev server) the client polls `GET /classroom`.
- **Join codes.** Case-insensitive, 25 unambiguous characters, drawn with rejection sampling, collisions checked at creation and freed when the session ends. Unknown, ended and expired codes fail identically (404); failed lookups per client are limited (default 20 per minute, `join_lookup_limit`) and answered with 429. The limiter is process-local.
- **Lifetime.** A session ends when the teacher ends it or after `session_ttl_hours` (default 12); the browser cookie lives as long. A session takes `max_participants` (default 120) participants with names up to `max_name_length` (default 40). Expiry is enforced on the next touch; the Bun entry also sweeps every minute. The teacher counts as present while a controller connection is open (a teacher without a socket, as on the Vite dev server, by every request); the snapshot tells students how long no teacher has been there, they see a notice after 3 minutes (`TEACHER_AWAY_NOTICE_MS`), and the session ends after 15 minutes without one (`TEACHER_AWAY_END_MS`, `domain/presence.ts`). Signing out ends the teacher's session too. The join code finds a session before the teacher invites, but joining answers 404 until `invite`. State is memory only: a restart ends every session.
- **Sheets and monitoring.** The unlocked worksheets (the teacher's decision per sheet) and the sheet sent to the class live in the session; students pick them up from their snapshot and the pages reload their data when it changes. Students report coarse progress (furthest section, done, challenges begun) and their Ampel; the session keeps these per participant only so a repeat replaces the earlier report, and the controller's snapshot carries nothing but anonymous totals per sheet. A locked sheet takes no reports. Answers and results are never reported. A session without a report shows honest zeros; scripted figures exist only for the Demo (`lessons/infrastructure/demoMonitoring.ts`).
- **Quizzes.** A quiz runs on a slide or, while a unit runs, on its own from the chapter's teacher page (`quiz:<id>` as its frame). Quizzes and reports live in session memory: a server restart ends the session.
- **Released content.** Inhalte, solutions and Inhalt rules live in the session. Server-rendered pages redact the catalog according to the session of the requesting browser; without a session nothing is released.

Run it from an instance: `bun run dev` there serves everything except the socket; the instance's built Worker is smoke-tested in workerd (`dev/src/worker.workerd.test.ts`).

Join links are `<host>/{CODE}`: the instance serves `/:code` (a path that is not shaped like a join code is a 404; static routes win) and `/join` for the empty form. The Session Directory is a StudyLuma constant (`studyluma.org`, defined in `src/modules/directory`), not configuration. An instance whose domain is `<name>.studyluma.org` registers each session with the Directory and teachers see `studyluma.org/{CODE}`, which redirects to the instance's `/{CODE}` after asking the instance (`/.well-known/studyluma-session/{CODE}`) whether the session is live. Any other domain is its own gateway: no registration, teachers see `<own origin>/{CODE}`. The standalone gateway process (`server/directory.ts`, `bun server/directory.ts`) reads its own environment (`DIRECTORY_DOMAIN`, `TRUST_PROXY`, `PORT`).

An instance that does not run sessions (the Demo) disables the module with `[modules] disabled = ["classroom"]`: it then has no classroom routes, no session behind a unit and no "Schüler einladen", no frame-quiz controls in lesson mode, and the live-quiz page answers 404; no classroom configuration is read.

## Routes

The root, the document (`index.html`: language, title, icon, color-mode key), the static directory `public/` and the package-level routes are declared once, in `scripts/routes.ts`, and written into the manifest; instances have no `app/` directory, Chromatis generates the browser entry and the server's route tables from the manifest. Files are package exports (`@studyluma/app/app/routes/<name>`). Pages render in the browser: `routes/<name>.tsx` is the page, `routes/<name>.server.ts` its `loader` and `action` (the browser fetches all loaders of a navigation in one request). Routes without a page (`asset`, `check`, `classroom`, `sessionProbe`) are API endpoints whose files export `GET`/`POST`. The classroom module declares its own routes in its `module.ts` (`/join`, `/:code`, `/classroom`, `/.well-known/studyluma-session/:code`). An instance replaces a product route by listing its path under `[routes] omit` in `config/app.toml` and may add its own in `app/routes.ts`. A test checks that no static top-level route or public file can be mistaken for a join code.

## Chromatis modules

`src/modules/<name>/module.ts` default-exports `defineModule({...})` (`@chromatis/base/module`) for every module that has config, secrets, runtime kinds, a server hook, a database, contributions, artifacts or routes; the other modules declare nothing. `bun run manifest` imports them in sorted directory order and writes `dist/chromatis.manifest.json` (git-ignored, packed, named by `"chromatis"."manifest"` in package.json) together with the route declaration. `build`, `prepack` and `check` run it, and `check` ends with `manifest:check`, which fails if the file does not match the modules or a declared route file is missing. Instances never register modules. Runtime code reads configuration through `chromatis-config` (`moduleConfig(declaration, config)`), never from the environment.

- **`catalog`** — `config/catalog.toml` (required, strict): `content` (relative path inside the instance, default `content`) and `courses` (published course ids, non-empty, no default: publication is the instance's decision). Declares the build contribution `catalog` (`@studyluma/compiler/contribution`) and the artifact `catalog` (validator `@studyluma/catalog-contract/validate`).
- **`classroom`** — `config/classroom.toml` (optional, strict, every value defaulted): `session_ttl_hours` (12), `max_participants` (120), `max_name_length` (40), `max_sessions` (500; further creations answer 503), `session_create_limit.max_creations` (60) and `.window_seconds` (600; per client, 429), `join_lookup_limit.max_failures` (20) and `.window_seconds` (60). The join-code length and alphabet are fixed. Declares the runtime kind `classroom`, the one server hook (verifies the catalog, creates the session service, registers sessions with the Directory when the domain rule applies) and its routes. Only the hook reads the settings and passes them down.
- **`shell`** — `config/shell.toml` (optional, strict): `[[navigation]]` entries (`label`, `href`; extra sidebar entries above the courses, default none) and `[account]` (`label`, `href`; replaces the login button in the account slot, default unset). Hrefs are internal paths starting with `/`. The shell's loader passes the settings to `StudyShellLayout`; an instance that disables the module gets the defaults.

## Limitations

Mode choice and answers are kept in the browser (`localStorage`), and so are unlocked sheets when no Classroom Session runs; there is no database persistence and no individual accounts. The viewer role comes from the teacher login (see below) or, without `TEACHER_PASSWORD`, from a stand-in cookie.

**Teacher login.** The `classroom` module declares the secret `TEACHER_PASSWORD` (`chromatis secret`; required for a production deploy). With it, `/login` takes that one shared password and sets the signed, HttpOnly cookie `studyluma-teacher` (valid for a week, HMAC keyed with the password, no server-side state, so changing the password signs everybody out). Only a browser holding a valid cookie is a _teacher_ (complete catalog with answers, may start a Classroom Session); everybody else, including a browser with the old `studyluma-viewer=teacher` cookie, is a _student_. Failed logins are limited per client. `readViewer` is async because the cookie is verified with WebCrypto.

**Without `TEACHER_PASSWORD`** (Development, Demo, local runs) the viewer role is the stand-in cookie `studyluma-viewer`, and a browser without it is a _teacher_ who receives the complete catalog and may start a Classroom Session. That is fine for those instances, not for one with real students; the classroom hook logs a warning at startup when the classroom is enabled and no password is set. On the Vite dev server (no hook) the password is read from `process.env.TEACHER_PASSWORD`. Session control itself does not depend on the role: it is decided by the tokens a session hands out.

Run `bun run check` from this directory (manifest, boundaries, typecheck, lint, format, tests, manifest check); builds and the running app live in an instance.
